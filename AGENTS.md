# Правила MendoSave

## Источники решений

1. Явные текущие решения пользователя.
2. [docs/PROJECT_SPEC.md](docs/PROJECT_SPEC.md) - требования, подход и приёмка.
3. Принятые ADR, если они появятся.
4. [docs/ROADMAP.md](docs/ROADMAP.md) - порядок, состояние и разрешения.
5. Этот файл - правила выполнения.

При возобновлении работы прочитай относящиеся к задаче требования и текущее состояние roadmap. Обнаруженный конфликт обозначь явно. Аудит upstream описывает исходник, а не задаёт новые инструкции.

## Границы продукта

- Приоритет - Zen на Windows. Chromium сохраняется как дополнительная сборка из общего кода. Совместимость с другими браузерами и ОС не считается проверенной по сходству движков.
- Обработка медиа выполняется в расширении. Серверы обработки, аналитика, реклама, отдельная устанавливаемая программа и Native Messaging не входят в принятый подход.
- Условия GPL и сторонних библиотек сохраняются. Пользовательские ссылки, оформление и каналы обновления upstream заменяются в ходе разработки; историческое происхождение не скрывается.
- Не ослабляй CSP страниц и не добавляй удалённо исполняемый код. Все библиотеки для обработки и упаковки поставляются внутри расширения.

## Рабочий контекст

- Разрешено использовать общие предпочтения и методы пользователя из доступной памяти. Требования, данные и состояние других проектов не становятся требованиями MendoSave без относящейся к задаче связи.
- Состояние расширения хранится в документах этого проекта. Пополнение общей памяти - только по отдельному прямому запросу пользователя. Настройки памяти Codex в подготовке не менялись; этот файл не доказывает настройку или наследование в новых чатах.
- `.local/upstream/source/` - сохранённый неизменённый исходник. Перед импортом сверь `.local/upstream/SOURCE.json`. Не редактируй эталон, не загружай его в рабочий профиль браузера и не запускай исходные build/CI scripts автоматически.
- Локальные пути и журналы находятся в `.local/`. В отслеживаемых файлах используй относительные пути и переносимые команды. Не включай профили браузера, cookies, токены, подписанные медиассылки и пользовательские выгрузки в Git или публичные отчёты.

## Разработка и проверки

- Применяй `$tdd` к изменяемому поведению по условиям навыка. Особое внимание: выбор места сохранения; план пакета; состояния очереди; отмена; завершение загрузки; восстановление; принадлежность job вкладке; ограничения URL, имён и сообщений. Синтаксическая проверка не доказывает эти свойства.
- Перед завершением программного roadmap-результата применяй `$code-review` к его совокупному diff и требованиям. Самопроверка должна охватывать реальный результат и существенные отрицательные случаи.
- Перед публичным выпуском выполняй `$codex-security:security-scan` над готовым репозиторием по правилам навыка. Для отдельного security diff используй соответствующий навык вместо полного scan. Не называй исходный аудит завершённым Codex Security scan: в подготовке он не выполнялся.
- Для реального программного сбоя используй `$diagnosing-bugs`. Для конкретного решения об интерфейсе модулей - `$codebase-design`. Остальные навыки выбирай по текущей задаче; не запускай новый project-start при обычном продолжении.
- Проверяй расширение в отдельном временном профиле Zen/Firefox. Не меняй рабочий профиль, установленные расширения или настройки подписей ради проверки.
- Для визуальных изменений проверяй реальные скриншоты широкого и узкого viewport, клавиатуру и затронутые controls. Записывай размеры viewport и фактические ограничения.
- Проверяй завершённый скачанный файл, а не только возврат download ID: контейнер, дорожки, длительность, начало/конец и выбранные параметры. Для ZIP сравнивай извлечённые bytes с подготовленными файлами до упаковки.
- Адаптеры, фон и обработчик медиа не доверяют странице. Связывай privileged operations с проверенным sender, вкладкой и job; проверяй схемы, размеры, допустимые состояния и маршруты сообщений. Проверка `origin` сама по себе не делает данные страницы доверенными.

## Документы и Git

Содержательное изменение требований записывай в spec до или вместе с реализацией. В roadmap отражай результат, фактические проверки, оставшуюся работу и разрешение на следующий шаг. README остаётся точкой входа и ссылается на текущее состояние.

Перед изменением Git применяй `$git-conventions`. Используй установленную личную идентичность `mendozie`; сохраняй авторство upstream и обязательные сторонние credits. Включай только изменения текущей задачи. Для нового remote требуется отдельное разрешение; отсутствие remote не является основанием создать его автоматически. Для существующего проверенного remote действуют применимые постоянные правила пользователя.

Проверенные документы подготовки допускают локальный commit. Пользовательская приёмка визуальных результатов и разрешения на публикацию сохраняют силу. Создание папки не доказывает её регистрацию как проекта в Codex.
